# Session store, roles, access control and seed accounts

Moved out of `AGENTS.md` (text unchanged) so that file stays short. Read this before changing the feature.

- `src/lib/roles.ts`, `src/lib/session-store.ts`, `src/components/session-provider.tsx`, `src/components/dashboard/role-badge.tsx`, `src/app/(protected)/layout.tsx`: the session and role store the UI reads (who is signed in, which role, what the role may SHOW). The protected layout passes four fields of the real session (`id`, `name`, `email`, `role`) to `SessionProvider`, which creates ONE vanilla Zustand store per provider (`createSessionStore`, React context): never a module-level `create()` store, because the module is shared by every request on the server and a global store would show one user's data to another (`e2e/session-store.spec.ts` checks that the module exports only factories, and `e2e/session-role-ui.spec.ts` checks two accounts never see each other's data, in the server HTML too). Read it with `useSessionUser()`, `useRole()`, `useIsPreview()`, `useCan(permissions)` (a boolean, so no wasted renders) and `useSessionActions()`; the pure selectors live in `session-store.ts` (`selectRole`, `selectCan`, ...). `roleCan` (`roles.ts`) answers exactly like Better Auth's `authClient.admin.checkRolePermission` (same split on commas without trimming, empty or null means `DEFAULT_ROLE`, any one role is enough; a test compares them over every role and permission) except that a role name that is only an inherited property (`constructor`, `toString`, `__proto__`) grants nothing instead of throwing, which Better Auth itself does. Everything here decides what is DISPLAYED and is never an access check: pages and APIs keep `requirePermission` and `withApiPermission`, and hiding a button is not protection. "Peran tiruan" (mock role): in demo mode (`DASHBOARD_DATA=demo`, decided on the server and fixed for the life of the store) the sidebar and the narrow-screen header show "Lihat sebagai", a native `select` with "Peran asli: <role>" plus one "<role> (tiruan)" per role in `permissions.ts`; picking one calls `previewAs`, so `useRole()` and `useCan()` follow it and a developer can see the screens of another role without a second account. It lives only in memory (a reload or another account clears it, `setUser` drops it when the id changes), is never sent to the server or stored, and changes only what the browser SHOWS: the server and every guard still follow the real role (`e2e` checks that previewing admin as a regular account still gets 403 from `/api/admin/notes` and the not-found page from `/admin`, and that a real admin previewing "Petugas" can still open `/admin`). In live mode there is no select, only "Peran: <chip>". `RoleBadge` carries `data-testid="role-badge"`, `data-role` (the effective role), `data-preview` and `data-preview-enabled`; it exists twice in the DOM (sidebar and bar), so query it by role and name or with `:visible`. The sidebar scrolls (`overflow-y-auto`) so the "Keluar" button stays reachable on short screens such as 1366x768 (a test measures it). Access control for the screen: `src/lib/access.ts` names the UI capabilities and maps each to permissions (`capabilities`: `adminArea` = `notes: read-any`, `manageCpe` = `cpe: manage`; frozen, `capabilityPermissions` returns a copy, `selectCanDo` follows the preview role), and `src/components/access.tsx` has `useCanDo(capability)` and `<Can to="adminArea" fallback={...}>` (or `<Can permissions={{ ... }}>` for a one-off; the type forbids giving both or neither; it shows nothing without a user). Components name a capability, never a raw permission object, so the screen policy changes in one place, and `e2e/access.spec.ts` pins the current matrix (admin can every capability, `user` none) so a change has to be deliberate. A new capability (handle alert, manage router, ...) is added there only AFTER its resource and action exist in `permissions.ts` and the server guards it. The first user is `AdminLink` (`dashboard/admin-link.tsx`): the "Buka admin" link no longer comes from an `isAdmin` prop and a database query in the app layout, it reads the role in the store, so a real admin has it in the server HTML (no flash) and the preview role moves it (`e2e/access-ui.spec.ts`, plus the live-mode case in `e2e/setup-gate.spec.ts`). `manageCpe` has no user yet: the CPE dialog is still a mock open to everyone, and gating it (and the handle-alert and add-router buttons) is the next step; do it with `<Can>` or `useCanDo`, and prefer keeping a denied action visible but `aria-disabled` with the reason as text over hiding it where an operator needs to know it exists. Authorization for changing data (server side, done): `permissions.ts` has `router: ["manage"]` and `alert: ["handle"]` (held by `admin`, not by the view-only `user`). `POST /api/routers` and `POST /api/routers/test` now use `withApiPermission(request, { router: ["manage"] }, ...)` (401 anonymous, 403 for a regular account BEFORE the body is read and before the server opens any connection; `e2e/write-authorization.spec.ts` proves a regular account causes zero outbound requests) and `POST /api/routers` no longer returns `passwordEnc`. Still open for the "Kelola Router" backend work: the test route lets an ADMIN make the server fetch `/rest/system/resource` on any host (no host validation, redirects are followed, raw error text can be echoed). The realtime ticket carries `perms` (see `backend/README.md`): `issueRealtimeTicket` takes them from the REAL role at issue time (`REALTIME_PERMS` maps `alert:handle` to the Better Auth permission), and the Go backend has `requirePerm` ready for the future `POST /api/v1/alerts/{id}/handle`. `npm run seed:accounts` (`scripts/seed-accounts.mjs`, logic in `seed-accounts-lib.mjs`) creates an admin (role `admin`) and a view-only account (role `user`): random 24+ character passwords printed ONCE (never written anywhere; `SEED_*_PASSWORD` env values are never echoed), idempotent (an existing account keeps its password; `--reset-password <admin|viewer|both>` makes a new one and revokes that account's sessions), a view-only email that is already an admin stops the run, and in production the default `@noc.local` emails are refused (`SEED_ADMIN_EMAIL`, `SEED_VIEWER_EMAIL`, `SEED_ADMIN_NAME`, `SEED_VIEWER_NAME` set them). Tests: `tests/seed-accounts.test.mjs` and `e2e/seed-accounts.spec.ts` (real sign-in with the seeded password).

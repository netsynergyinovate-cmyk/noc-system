# Dashboard, alerts, anomalies, incident cards, handling and the alert badge

Moved out of `AGENTS.md` (text unchanged) so that file stays short. Read this before changing the feature.

## Dashboard data flow, Alert page, Deteksi Anomali, correlation, incident cards, alert sound

- `src/lib/dashboard/`, `src/components/dashboard/`: the dashboard UI with mock data. `store.ts` takes snapshot/delta messages; `mock-feed.ts` is the stand-in for the backend WebSocket and is replaced inside `dashboard-feed.tsx`. The traffic panel's range picker (5 menit/1 jam/6 jam/24 jam/7 hari, `ranges.ts`) reads history and incident markers through `history.ts` (`loadTrafficHistory`, `loadIncidents`), which currently build deterministic mock data; swap them for the backend: `GET /api/v1/traffic/history` already exists (Go backend, needs `DATABASE_URL`; `range=1h|6h|24h|7d` gives the same steps the picker uses, see `backend/README.md`), `GET /api/v1/incidents` does not exist yet. The map (`customer-map.tsx`) takes focus requests through the store: `useDashboardStore.getState().focusMap(customerId)` zooms to that customer, rings them, and shows a banner with "Tampilkan semua"; `/app?focus=<customerId>` sends the same request on load. Anything that wants to point at an incident (incident list, notifications) should call `focusMap`, not touch the map. The Deteksi Anomali page (`/app/anomali`, `anomaly-board.tsx`, `lib/dashboard/anomalies.ts`) lists the same incidents as the chart markers with router, customer and measured value; `anomalyRules` there is the single source for thresholds and must match the Go rule engine. `loadAnomalies` is the seam for a future `GET /api/v1/anomalies`; the mock data is a function of time only, so a given `now` always gives the same list. Active alerts (`lib/dashboard/alerts.ts`) are the contract for a future `GET /api/v1/alerts?status=active`: whole-second `startedAt`/`detectedAt` plus `timeSource` (`event` from the router, `poll` from polling) and `timeUncertaintySeconds`; render times with `AlertTime`, never a bare date string. Each alert also carries `location` (ODP/address/coordinates for customer alerts, router name with null coordinates for router alerts); render it with `AlertPlace` and never invent a point for a router. The Alert page (`/app/alert`, nav label "Alert") shows two lists read from one Zustand store, `useAlertStore` (`lib/dashboard/alert-store.ts`): the dashboard feed (`DashboardFeed`, mounted once in the app layout) loads a snapshot and then applies `alerts` hub messages (`lib/dashboard/alert-sync.ts`: the full active list plus the alerts that ended since the last message, only when something changed; `createMockAlertHub` stands in for the Go hub), and `AlertBoard`, `AnomalyBadge` and nothing else read it, so there is no per-page polling for alerts any more and moving between pages shows no loading skeleton. A pure reducer (`snapshotState`, `messageState`, `pruneResolved`) keeps unchanged alerts as the same objects, drops expired history and applies repeated messages harmlessly; `e2e/alert-sync.spec.ts` replays hub plus reducer over random time steps and requires the result to equal the truth at every step. An alert that just ended moves from the active list (`active-alert-list.tsx`) to the top of the history (`resolved-alert-list.tsx`) in one store update: never in both, never in neither. The cut is exact, `endedAt > now` is active and `endedAt <= now` is history, and `e2e/resolved-alerts.spec.ts` checks it to the second. `loadAlertLists` is the REST backfill seam (initial load and resync once the real backend exists): it loads active first and history second, and `reconcileAlertLists` (also used by the store) drops from the active list anything already in history, so a backend that serves them as two requests keeps the guarantee (the opposite order would let an alert vanish for one poll). Resolved alerts (`ResolvedAlert`) are the contract for a future `GET /api/v1/alerts?status=resolved&from=&to=`: the same fields as active ones with `endedAt` filled, and no root source/impact yet (correlation is only computed for active alerts). The end time has its own precision, `endTimeSource` and `endTimeUncertaintySeconds`, separate from the start's because an alert can start from polling (the on-down webhook failed) and end from the on-up event; render it with `AlertEndTime` (marker attribute `data-end-time-source`, wording about recovery via `describeTimeSource(..., "end")`), while the start keeps `AlertTime` and `data-time-source`, so a row never has two markers with the same attribute. The mock generator is shared (`alertInSlot` in `alerts.ts`), so everything about an alert except the end fields is identical before and after it moves. The history covers `ALERT_HISTORY_SECONDS` (7 days, like the anomaly page), newest ending first, and is paged client-side (`ALERT_HISTORY_PAGE_SIZE`, `lib/dashboard/paging.ts`; the page buttons use `aria-disabled` so keyboard focus survives the last page). The history also has search and filters (pure logic in `lib/dashboard/resolved-filter.ts`, UI in `resolved-filters.tsx`): free text where every word must match (case-insensitive, over what the row shows: customer name, PPPoE username, router, ODP, address, kind and severity labels and the measured text; alert ids are not searched), plus kind, severity, router and "selesai dalam" 1/6/24 hours, which is measured from the start of the current minute (`useNowMinute`) and strict to the second at the boundary. Every option shows how many alerts choosing it would leave (`resolvedFacetCounts`; `e2e/resolved-filter.spec.ts` checks every option in 150 random filter states, and the UI spec checks the option texts), changing any filter returns to page 1, and no match shows a message with a "Tampilkan semua alert selesai" button. Keep `matches`, `filterResolvedAlerts` and `resolvedFacetCounts` in step; filters are component state, not URL state, like the anomaly page's. The active card (`ActiveAlertList`) heads itself with per-severity chips (`1 kritis`, `4 peringatan`, or `Semua normal` when empty; numbers and words, never colour alone) built from `summarizeAlertSeverity` in `alerts.ts`, the same function the dashboard `AnomalyBadge` uses, so the badge and the card always agree on counts and tone; the card carries `data-count`, `data-critical`, `data-warning` and `data-tone` for tests. The `--success` and `--warning` theme tokens are deliberately dark enough that text on their own 10% tint (`bg-success/10`, `bg-warning/10`) stays above 4.5:1; `e2e/active-alert-card.spec.ts` measures it in both themes, so check it before lightening them. A new alert makes a sound once (`AlertSoundController` in the app layout, so it works on every page): `createAlertSoundTracker` (`lib/dashboard/alert-sound.ts`, pure) treats the alerts present when the page opens as the baseline, counts each id as new exactly once even if it disappears and returns, and keeps remembering ids while muted so unmuting never replays old incidents; several new alerts in one store update make one sound, the two-tone critical pattern if any is critical, otherwise the single warning tone (`soundPatterns`, all under one second and quiet). `lib/dashboard/sound-engine.ts` plays them with Web Audio and holds the mute choice (`localStorage` key `alertSound`, session-only if storage is blocked). Browsers refuse sound until the user interacts, so the first click or key unlocks it (the `AlertSoundToggle` in the sidebar and mobile header reads "menunggu klik" until then); an alert that arrives while locked stays silent and is not replayed later. Turning sound on plays one short test tone. Tests cannot hear, so `e2e/alert-sound-ui.spec.ts` replaces `AudioContext` with a recorder via `addInitScript` and checks the tones scheduled; wait for the page to be ready (`ready()`) before the first click or the unlock listener is not attached yet. Both lists show start times to the second with the time-source marker, and history rows carry `data-testid="resolved-alert-row"` (active rows keep `alert-row`); history rows show the same location cell and "Sorot di peta" link as active rows (`AlertPlace`, `HighlightOnMap`, which accept any alert with `customerId` and `location`), and the pair moves with the alert unchanged (`e2e/resolved-alert-location.spec.ts`). `e2e/resolved-alert-location-data.spec.ts` checks every resolved alert over four weeks of mock data against the map's customers and routers (same point, ODP and address; a router alert never gets an invented point), and the UI spec also requires the focus ring to be centred on the map after the click and "Tampilkan semua" plus Back to land on the history again. When a test follows a "Sorot di peta" link to the map, let the fake browser clock run (`clock.install` only): a frozen `Date.now()` (`setFixedTime`) stalls Leaflet's fly animation and the zoom never reaches 16, so pick a moment whose list stays the same for the next 30 seconds instead; the history's start and end times are pinned to the second twice over: `e2e/resolved-time-display.spec.ts` compares with `Intl` in several time zones, and `e2e/resolved-time-seconds.spec.ts` compares with integer arithmetic that does not use `Intl` (every second 00-59, hour 00 never written as 24, month/year/leap-day boundaries with Indonesian month names, half-hour zones such as Asia/Kolkata and Asia/Kathmandu, later pages), so a formatter bug cannot hide behind a test that shares the same library; each customer alert has a "Sorot di peta" link to `/app?focus=<customerId>` (router alerts have no point and say so); build and read such links only through `lib/dashboard/map-focus.ts` (`mapFocusHref`, `readFocusId`) so the limits stay in step; `AnomalySubject` renders who/what is affected for both pages. Running durations tick through `useNowSeconds` (one shared timer, `clock.ts`); only components that call it re-render each second, so keep it out of tables and lists as a whole. The anomaly list filters (kind/severity/status, `lib/dashboard/anomaly-filter.ts`) show faceted counts next to every option, and the per-kind cards double as filter buttons; keep `facetCounts` and `filterAnomalies` in step (a test checks every combination). `loadAnomalies` lives in `lib/dashboard/anomaly-feed.ts`: its active entries are exactly `mockActiveAlerts`, so the dashboard `AnomalyBadge` (links to `/app/alert`), the active list on the Alert page and the Deteksi Anomali page always agree on how many are active. Their ended entries do not match in mock data: the anomaly page still takes its history from the traffic chart's incident markers (`mockIncidents`) while the Alert page's history comes from `mockResolvedAlerts`; a real backend reads both from `network_logs`. `lib/dashboard/correlation.ts` (`correlateAlerts`) groups active alerts that likely share one cause (same ODP, same router, a burst of offline customers, router alert plus its customers); it is pure, takes alert time uncertainty into account, and is frontend-only for now (the Go rule engine does not do it). Every `Anomaly`/`ActiveAlert` carries `rootSource`, `affectedCustomers` (proven, i.e. have their own alert), `servedCustomers` (upper bound) and `correlationId` (`lib/dashboard/incident-root.ts`); `mockActiveAlerts` fills them from the correlation groups, `toAnomaly` gives lone defaults. The incident cards on the Deteksi Anomali page show them. `lib/dashboard/incident-cards.ts` (`buildIncidentCards`, `loadIncidentCards`, `summarizeIncidentCards`) turns the active alerts into one card per correlation group, each with root source, affected/served counts, the oldest member's time fields (render with `AlertTime`), its member alerts and a `focusCustomerId` for `mapFocusHref`; `loadIncidentCards` is the REST seam for a future `GET /api/v1/incidents/cards?status=active` (initial load or backfill), but the UI no longer polls it: cards arrive as `incidents` messages from the hub (`lib/dashboard/incident-sync.ts`: full list right after the snapshot, then only when it changes; `createMockIncidentHub` stands in for the Go hub inside `DashboardFeed`, which is now mounted once in the app layout, not per page), land in the store as `incidentCards` with unchanged cards keeping their object identity, and `IncidentCardList` reads them from there; and `e2e/incident-cards.spec.ts` pins the contract. The correlation rules themselves are pinned three ways: hand-built cases (`e2e/correlation.spec.ts`), timelines through the hub and store plus seeded random sets compared against an independently written reference and checked for closure/monotonicity (`e2e/correlation-flow.spec.ts`), and a cross-page acceptance test on the mock data (`e2e/incident-acceptance.spec.ts`). Change a window or rule in `correlation.ts` and expect those to tell you. The Deteksi Anomali page renders them with `incident-card-list.tsx` (`IncidentCardList`: polled every 5 s, one `article` per card, a "Lihat rincian" toggle that opens the member alerts as compact rows of its own, open state kept per card id across refreshes, a "Sorot di peta" link when `focusCustomerId` is set); `e2e/incident-card-list.spec.ts` covers it with a fake browser clock.

## "Tandai ditangani" (handling an alert)

- `src/lib/dashboard/handled-registry.ts`, `alert-actions.ts`, `src/components/dashboard/handle-alert-dialog.tsx`: "Tandai ditangani" (PRD flow A step 7: the operator closes an active alert and it moves to the history). Every active alert card on the Alert page has the button in its footer row, next to the ticket and map buttons (`AlertCardList`, shown only when `onHandle` is passed), so the main action never hides behind a horizontal scroll. The incident-card detail rows (`incident-card-list.tsx`) are separate and stay read-only. It opens a Radix `AlertDialog` (`ui/alert-dialog.tsx`, added with shadcn; `motion-reduce:animate-none!` was added to its overlay and content) that names the alert (kind, subject, severity, start time) and the operator (`user.name || user.email`, passed from `alert/page.tsx` through `AlertBoard` to `ActiveAlertList`; the real backend takes it from the session), with focus on "Batal". `useHandleAlert` runs the phases: confirm; saving (one request at a time, buttons use `aria-disabled` and never `disabled` so keyboard focus stays, and the dialog cannot be closed); failed (the reason is written in the dialog, the button becomes "Coba lagi", the alert stays active); done. "Alert already inactive" (it ended by itself, or another operator marked it while the dialog was open) is derived from the latest active list during render, not stored, so it shows at once and needs no effect. Radix returns focus only to a `Trigger` and this one dialog has none, so `restoreFocus` does it by hand: back to the button that opened it, or to the list region (`AlertCardList`'s `regionRef`) when that button is gone, which is the case after success because the row has moved. Success also writes a line in the card's `role="status"` description (`HandledNotice`), because the row it concerns is gone. The data side: `ResolvedAlert` gained `handledBy` (null for alerts that ended by themselves) and a third `endTimeSource`, `"operator"` (type `AlertEndSource`), with `endedAt` the second the server processed the confirmation and `endTimeUncertaintySeconds` 0; everything else about the alert is identical before and after. `handledRecord` in `alerts.ts` is the one rule both lists use: a record counts only when `detectedAt <= at < natural endedAt` and `at <= now`, anything else (clock shift, hand-edited storage) is ignored. `mockActiveAlerts` and `mockResolvedAlerts` take the records as an explicit `handled` map (default none), so the pure functions and every older test are unchanged, and the glue that stands in for the backend reads `currentHandled()`: the alert hub's `mockSource`, `createMockIncidentHub`, `loadAnomalies`, and `loadActiveAlerts`/`loadResolvedAlerts`/`loadAlertLists` (which also accept the map, for tests). That is why the dashboard badge, the Alert page, the Deteksi Anomali page and the incident cards agree after a handle; the anomaly page's own history (chart markers) does not list handled alerts, just as it does not list naturally ended ones (the known mock mismatch). `handled-registry.ts` is the mock server's database: localStorage key `alertHandled` (a list of `{id, at, by}`, kept 7 days like the history, validated entry by entry on read, memory only if storage is blocked, re-read whenever its text changes so another tab's mark shows up). `createMockAlertActions` (`alertActions`) is the mock server: 300 ms of latency so "Menyimpan…" is visible; it judges at processing time (`not-active` is the 409 stand-in; `offline` stands in for a failed fetch and reads `navigator.onLine`, which `context.setOffline` flips in tests), records `{id, at, by}` and answers with the same `ResolvedAlert` the hub and REST give. `useAlertStore.markHandled` applies the answer with `handledState` (active to the top of the history in one update; applying it twice, or after the hub message that carries the same alert, changes nothing), and the next hub tick corrects siblings whose correlation impact changed. Mock-only limit: a mark written by another tab in the same second after this tab's hub check reaches this tab's history on the next resync (its active list is right at once); the tab that marks is not affected. The history row writes `ditangani oleh NAME` under the end time (`data-end-time-source="operator"`, `data-handled`), and `describeHandled` also feeds `searchableText`, so searching "ditangani" or the name works (there is no filter dimension for it). The API the real backend must serve (`POST /api/v1/alerts/{id}/handle`) is in `backend/README.md` ("Menandai alert ditangani"). Tests: `e2e/alert-handling.spec.ts` (logic: records, both lists over two days with random marks must stay a partition and lose nothing, the mock server, `handledState`, and a random handle-and-advance replay that must equal the truth after every hub message) and `e2e/alert-handle-ui.spec.ts` (page: button names, dialog, focus, moving to the history, persistence across reload, the other pages, saving, offline, ended while open, marked in another tab, search, 390 px, reduced motion). To hold the "saving" phase use `clock.install` plus `clock.pauseAt` (no `setFixedTime`) so the 300 ms timer waits for `clock.runFor`; when a test searches the history use an operator name that no mock customer has (customers are named Budi, Dewi, ...), because the real directory is searched too.

## Alert count badge in the menu

- `src/lib/dashboard/alert-badge.ts`, `src/components/dashboard/alert-count-badge.tsx`, `app-nav.tsx`: the badge with the active alert count on the "Alert" menu item, in the sidebar and in the narrow-screen bar, so the count is visible on every page and changes by itself when the hub sends an `alerts` message. The numbers come from `summarizeAlertSeverity` over `useAlertStore().active` (the same function as the active card's chips and the dashboard `AnomalyBadge`, so the three always agree) through the pure `alertBadge`: `null` until the list arrives (never an invented zero), the text capped at `99+` (`ALERT_BADGE_MAX`) while the sentence keeps the real number, zero shows only a green check, the sentence reads `5 alert aktif, 1 kritis` and gains `(koneksi terputus, data terakhir)` when the connection dropped. The tone is told by icon shape and number as well as colour. The link's accessible name must stay exactly "Alert" (many specs find it with `{ name: "Alert", exact: true }`), so the pill is `aria-hidden` inside the link and the sentence travels outside it: `AlertCountAnnouncement` is a sibling `role="status"` region, always mounted so the first content is announced, which the link references with `aria-describedby`; the ids come from `useId` because the sidebar and the bar both exist in the DOM. The subscriptions live in those two child components, so `AppNav` (which only knows the pathname) does not re-render on alert messages. The 10% tint is laid over an opaque `bg-card` (`bg-linear-to-r from-x/10 to-x/10`) instead of over whatever is behind the pill: on the current page the link is `bg-secondary`, and the warning tint over that dropped to 4.26:1. Tests: `e2e/alert-badge.spec.ts` (pure) and `e2e/alert-count-badge.spec.ts` (page: same count and tone on every page, name and description, the zero state, updates without a reload by moving the fake clock, drops at once when an alert is marked handled, 390 px, and contrast of every tone in both themes on the current page and on another).

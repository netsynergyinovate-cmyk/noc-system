# Billing sync (Go backend)

Moved out of `AGENTS.md` (text unchanged) so that file stays short. Read this before changing the feature.

- `backend/internal/billing/`, `backend/internal/httpapi/billing.go`, `backend/internal/state/billing.go`, `drizzle/0006_billing_sync.sql`: the REAL billing sync (the Billing page still shows mock data until the frontend swaps `loadBilling`/`loadBillingSync` for the endpoints). Read "Sinkron billing (implementasi)" in `backend/README.md` first; the points that bite: (1) the matching rule exists twice, in TS (`matchBilling`) and in Go (`MatchInvoices`), and a shared 543-case file (`backend/internal/billing/testdata/match_cases.json`, checked by Go tests and `e2e/billing-conformance.spec.ts`) fails whichever side drifts; (2) the scraper's `DefaultProfile()` is a generic guess and MUST be matched to the real billing site's HTML before use; (3) a failed sync never touches `billing_status` or `customers.billing_status`, a source with zero invoices or one that shrank below `BILLING_DROP_PERCENT` is refused, and only network, timeout and 5xx errors are retried (a rejected login is never retried and 3 in a row slow the schedule to every 6 hours); (4) billing runs only when `BILLING_URL`, `BILLING_USERNAME`, `BILLING_PASSWORD` and `DATABASE_URL` are all set (none set: one info line; partly set: the backend refuses to start); (5) `GET /api/v1/billing` and `/billing/sync` are read-only behind the realtime ticket (view-only tickets may read), their shape is locked by golden files and `e2e/billing-contract.spec.ts`, and `billingChanges` reaches the dashboard through `state.Manager.SetBillingStatuses` and the hub (`e2e/billing-ws-contract.spec.ts`); (6) the Go `Manager` has no customer loader yet, so live badges only move once the collector loads customers from the database. Go tests that need PostgreSQL skip without `TEST_DATABASE_URL`, so run them with `npm test`; goldens are rewritten with `UPDATE_GOLDEN=1 npm test`.
